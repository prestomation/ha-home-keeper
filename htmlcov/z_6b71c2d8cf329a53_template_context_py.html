1"""The Jinja render context Home Keeper hands every user-written template. 

2 

3Two surfaces render user templates, and they must see the same names: 

4 

5* a declarative companion's ``name_template`` / ``notes_template``, rendered per 

6 matched entity by :mod:`declarative_companion_sync`; 

7* a ``template``-mode sensor binding's trigger, rendered per evaluation pass by 

8 :mod:`sensor_watcher`. 

9 

10The context lived in ``DeclarativeCompanionSync`` while only the first surface 

11existed. It moved here rather than growing a second copy, because 

12``declarative_companion_sync`` imports ``sensor_watcher`` (for 

13``async_mark_tasks_new``), so the watcher cannot import it back. A second copy is 

14worse than the import cycle it avoids: the two would drift, and a recipe's task name 

15would then read a different ``{{ state }}`` from the trigger that opened it. 

16 

17HA-bound: it reads the entity, device and area registries. The pure side never calls 

18it. 

19"""

40# Templates Home Keeper has already compiled, per config entry's Home Assistant. 

41# 

42# Home Assistant caches compiled template code on its shared environment, but 

43# ``TemplateEnvironment.template_cache`` is a **WeakValueDictionary**: the only strong 

44# reference to the compiled code is the ``Template`` object's own ``_compiled_code``. 

45# Build a fresh ``Template`` for each entity and the previous one is collected, the 

46# cache entry goes with it, and every render re-parses the Jinja source. 

47# 

48# That is 90x the cost of the render it precedes — ~500us to parse against ~6us to 

49# render — so a recipe at the 500-entity cap spent about a quarter of a second of 

50# event-loop time parsing one unchanged expression, on every pass. Holding the 

51# ``Template`` keeps Home Assistant's own cache warm and the parse happens once. 

52# 

53# Capped, because the recipe preview renders on every keystroke and each draft is a 

54# different source: without a bound, typing a template would grow this forever. 

55# 

56# Keyed by ``(strict, source)`` rather than by source alone. ``Template`` asserts that 

57# ``strict`` never changes for one object, and the two callers disagree: a trigger 

58# renders strict so a typo cannot read as false, while a task name renders lax so 

59# ``{{ attributes.latest_version or 'unknown' }}`` keeps working. Sharing one object 

60# between them would trip that assertion the first time a user wrote the same text in 

61# both boxes. 

62_TEMPLATE_CACHE: HassKey[dict[tuple[bool, str], Template]] = HassKey( 

63 "home_keeper_template_cache" 

64) 

65_TEMPLATE_CACHE_MAX = 64

68def cached_template( 

69 hass: HomeAssistant, source: str, *, strict: bool = False 

70) -> Template: 

71 """A ``Template`` for *source*, reused across entities and evaluation passes. 

72 

73 Reuse is safe because rendering does not mutate the template: ``async_render`` 

74 takes its variables per call, which is how Home Assistant drives its own 

75 config-defined templates. Callers must keep the render flags constant, though — 

76 ``Template`` asserts that ``limited`` and ``strict`` never change for one object — 

77 so *strict* is part of the cache key and callers pass the same value every time. 

78 

79 Kept on ``hass.data`` rather than in a module-level dict so the cache cannot 

80 outlive the Home Assistant it is bound to. 

81 """ 

82 cache = hass.data.get(_TEMPLATE_CACHE) 

83 if cache is None: 

84 cache = hass.data[_TEMPLATE_CACHE] = {} 

85 key = (strict, source) 

86 template = cache.get(key) 

87 if template is None: 

88 if len(cache) >= _TEMPLATE_CACHE_MAX: 

89 # Plain FIFO rather than an LRU: the entries worth keeping are the handful 

90 # of saved recipes that render every pass, and they are re-added the next 

91 # time they render. The churn this bounds is a preview draft, which is 

92 # never rendered twice. 

93 cache.pop(next(iter(cache))) 

94 template = cache[key] = Template(source, hass) 

95 return template

98def registry_projection(hass: HomeAssistant, entity_id: str) -> dict[str, Any]: 

99 """The registry fields :func:`template_variables` needs, for *entity_id*. 

100 

101 Falls back to a projection carrying only the ``entity_id``. A managed task always 

102 names its entity, but the registry entry can already be gone (the entity was 

103 removed and the reconcile pass that drops the task has not run yet), and a 

104 template-mode task can be bound to an entity that has no registry entry at all. 

105 The templates that read ``{{ entity_id }}`` and the live state still render. 

106 """ 

107 found = er.async_get(hass).async_get(entity_id) 

108 if found is None: 108 ↛ 109line 108 didn't jump to line 109 because the condition on line 108 was never true

109 return {"entity_id": entity_id} 

110 device = dr.async_get(hass).async_get(found.device_id) if found.device_id else None 

111 return { 

112 "entity_id": found.entity_id, 

113 "device_id": found.device_id, 

114 # The effective area, as a recipe's selection pass projects it: most entities 

115 # take their area from their device. With the entity's own area alone, a 

116 # trigger that reads ``area_id`` would disagree with the recipe preview and 

117 # with the task notes for the same entity. 

118 "area_id": effective_area_id(found.area_id, device.area_id if device else None), 

119 "platform": found.platform, 

120 "name": found.name, 

121 "original_name": found.original_name, 

122 }

125def template_variables(hass: HomeAssistant, entry: dict[str, Any]) -> dict[str, Any]: 

126 """Assemble the Jinja render context for one entity. 

127 

128 *entry* is a registry projection — either the one a declarative companion's 

129 selection pass already built, or the one :func:`registry_projection` builds for a 

130 lone entity id. Only the keys listed below are read, so both shapes fit. 

131 

132 The context flattens registry + state + device + area lookups so a template writer 

133 only ever sees ``{{ device_name }}`` — never ``{{ device.name_by_user or 

134 device.name }}``. Attribute access on the entity's state is exposed as 

135 ``attributes.<key>`` so a Firmware Update template can say 

136 ``{{ attributes.latest_version }}``. 

137 

138 These names are a public contract: they appear in the panel's helper text, in the 

139 User Guide, and in every recipe a user has already saved. Add to them freely; 

140 never rename one. 

141 """ 

142 entity_id = entry["entity_id"] 

143 state = hass.states.get(entity_id) 

144 friendly = None 

145 state_value: Any = None 

146 attributes: dict[str, Any] = {} 

147 if state is not None: 

148 state_value = state.state 

149 attributes = dict(state.attributes) 

150 friendly = attributes.get("friendly_name") 

151 friendly = friendly or entry.get("name") or entry.get("original_name") or entity_id 

152 device_name = None 

153 if entry.get("device_id"): 

154 device = dr.async_get(hass).async_get(entry["device_id"]) 

155 if device: 

156 device_name = device.name_by_user or device.name 

157 area_name = None 

158 if entry.get("area_id"): 

159 area = ar.async_get(hass).async_get_area(entry["area_id"]) 

160 if area: 

161 area_name = area.name 

162 return { 

163 "entity_id": entity_id, 

164 "friendly_name": friendly, 

165 "device_id": entry.get("device_id"), 

166 "device_name": device_name, 

167 "area_id": entry.get("area_id"), 

168 "area_name": area_name, 

169 "integration": entry.get("platform"), 

170 "state": state_value, 

171 "attributes": attributes, 

172 }
