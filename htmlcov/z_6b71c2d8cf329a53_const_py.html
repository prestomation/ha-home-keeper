222# A condition-driven task with no schedule. An owner integration arms it (via 

223# ``trigger_task`` or by creating it) when a condition becomes true and clears it 

224# (via ``complete_task``) when the condition resolves. Its ``next_due`` *is* its 

225# state: ``None`` = dormant (invisible to every time surface), a timestamp = 

226# active/due-now. See docs/INTEGRATING.md "Condition-driven (triggered) tasks". 

227REC_TRIGGERED = "triggered" 

228# A user-scheduled do-once task. It carries its own ``due`` datetime (the chosen 

229# due date); ``compute_next_due`` reads it back, and completing the task sets 

230# ``next_due = None`` permanently (no rescheduling) — it goes dormant like a 

231# triggered task, but undoing the completion re-arms it to ``due`` (its state is 

232# history-driven, not condition-driven). See docs/EVENTS.md / README. 

233REC_ONE_OFF = "one-off" 

234# A sensor-based task: Home Keeper derives its armed/dormant state from a bound 

235# entity rather than the clock. Like ``triggered`` its ``next_due`` *is* its 

236# state (``None`` = dormant, a timestamp = armed/due-now), but Home Keeper itself — 

237# not an external owner — arms it via a pure evaluator fed by the live reading. The 

238# binding lives in ``task["sensor"]`` (see ``models.normalize_sensor`` / 

239# ``sensor_tasks.py``). Three modes: ``usage`` (a meter — due after the reading 

240# advances ``target`` units since the last completion), ``threshold`` (due when 

241# the reading crosses a numeric comparison) and ``state`` (due when the entity enters 

242# a given state). See docs/SENSOR_TASKS_PLAN.md. 

243REC_SENSOR = "sensor" 

244RECURRENCE_TYPES = [REC_FLOATING, REC_FIXED, REC_TRIGGERED, REC_ONE_OFF, REC_SENSOR]

384# ── Localized name for reconciler-generated wear-part tasks ───────────────────── 

385# The wear-part reconciler auto-generates a maintenance task name like 

386# "Replace {part} ({asset})". Unlike the panel's static UI (translated client-side 

387# per viewer), a task's ``name`` is server-side global data — a single value shared 

388# by every to-do item, calendar event, notification, device-page entity, and API 

389# consumer. So we translate it once, at write time, into Home Assistant's configured 

390# language (``hass.config.language`` — the household's primary language), and store 

391# that. ``store.reconcile_part_tasks`` resolves these and hands them to the pure 

392# reconciler; a language change relocalizes every generated name via an entry reload 

393# (see ``__init__`` EVENT_CORE_CONFIG_UPDATE listener). The 16 languages match the 

394# panel's shipped locales. ``{part}``/``{asset}`` are filled from the wear part and

459def _pick_localized(table: dict[str, str], language: str | None) -> str: 

460 """Resolve *language* against *table*: exact → case-insensitive → base → English. 

461 

462 Mirrors the panel's ``i18n.resolve`` so a code like ``"pt-BR"`` matches exactly, 

463 ``"en-GB"`` falls back to ``"en"``, and anything unknown lands on English. Pure — 

464 safe to unit-test without a Home Assistant runtime. 

465 """ 

466 lang = language or DEFAULT_LANGUAGE 

467 if lang in table: 

468 return table[lang] 

469 low = lang.lower() 

470 for key, value in table.items(): 

471 if key.lower() == low: 

472 return value 

473 base = low.split("-")[0] 

474 for key, value in table.items(): 

475 if key.lower() == base: 

476 return value 

477 return table[DEFAULT_LANGUAGE]
